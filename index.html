    GitHub Guide: Basics, then Advanced

    Learn GitHub with clear “why → how,” real commands, diagrams, and practice checklists. Finish the basics track, then keep going into advanced workflows.

    Live: krishant624.github.io/github-guide

    Basics 1–13 Advanced A1–A6 No CDN / works offline

    1. Core concepts

    Git vs GitHub

    Git is the version-control tool on your computer. GitHub hosts Git repos and adds collaboration (PRs, issues, Actions, Pages).

    Repository = project + history. Commit = snapshot + message. Branch = pointer to a commit line. Remote = named URL (usually origin). Fork = your copy of someone else’s GitHub repo.

    2. Setup

    git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase false

    SSH (recommended)

    ssh-keygen -t ed25519 -C "you@example.com"
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub
# paste into GitHub → Settings → SSH and GPG keys
ssh -T git@github.com
    Warning

    For HTTPS, use a Personal Access Token—not your GitHub password. Never commit tokens.

    Practice checklist

    3. Creating and cloning repos

    git clone git@github.com:USERNAME/REPO.git
cd REPO

# or start local, then push
mkdir my-project && cd my-project
git init
echo "# My Project" > README.md
git add README.md
git commit -m "Initial commit: add README"
git branch -M main
git remote add origin git@github.com:USERNAME/REPO.git
git push -u origin main

    Add README.md (what/how), .gitignore (what not to track), and a LICENSE when others may use the code.

    4. Daily workflow

    git status
git pull
# edit files...
git diff
git add path/to/file
git commit -m "Fix login timeout on slow networks"
git push
git log --oneline --graph -n 15
    • fetch downloads updates; pull fetches and integrates.
    • diff / diff --staged show unstaged vs staged patches.

    Practice checklist

    5. Branching and merging

    git checkout main && git pull
git checkout -b feature/add-search
# commit work...
git push -u origin feature/add-search

    Merge preserves topology. Rebase replays commits for a linear history—avoid rebasing shared commits; use --force-with-lease only on your branch if you must rewrite.

    Conflict example

    <<<<<<< HEAD
title = "Homepage"
=======
title = "Home"
>>>>>>> feature/rename
# edit to the correct final lines, then:
git add config.toml
git merge --continue   # or: git rebase --continue

    6. Pull requests

    A PR proposes merging a branch and is where review happens. Push your branch → open PR → describe what/why/how to test → request reviewers.

    Merge strategyUse when
    Merge commitKeep full branch history
    Squash and mergeWant one clean commit on main
    Rebase and mergeLinear history; commits already tidy

    7. Collaboration

    git remote add upstream git@github.com:ORIGINAL/REPO.git
git fetch upstream
git checkout main
git merge upstream/main
git push origin main

    Use Issues for work tracking, labels/milestones/assignees for triage, @mentions for attention, and Projects boards for Todo → Doing → Done.

    8. Undoing things safely

    git restore file                 # discard unstaged edits
git restore --staged file        # unstage, keep edits
git commit --amend               # fix last commit (if not shared)
git revert abc1234               # undo with a new commit (safe on main)
git stash -u && git stash pop
git reflog                       # find “lost” commits
    Warning

    reset --hard destroys uncommitted work. Prefer restore / revert / reflog until you’re sure.

    9. GitHub Actions basics

    name: CI
on:
  push: { branches: [main] }
  pull_request: { branches: [main] }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "20" }
      - run: |
          npm ci
          npm test

    Save as .github/workflows/ci.yml. Deeper patterns are in Advanced.

    10. Repo settings and security

    • Enable 2FA on your account.
    • Protect main: required reviews, required checks, no force-push.
    • Add CODEOWNERS, Actions secrets, and Dependabot alerts/updates.
    # .github/CODEOWNERS
*       @your-username
/docs/  @docs-team

    11. GitHub Pages

    1. Put index.html at repo root; add empty .nojekyll.
    2. Settings → Pages → Deploy from branch → main / root.

    URL shape: https://USERNAME.github.io/REPO/ — this site: https://krishant624.github.io/github-guide/

    12. Troubleshooting

    # push rejected → integrate first
git pull --rebase origin main
git push

# detached HEAD → keep work on a branch
git switch -c recover-work

# auth
ssh -T git@github.com
git remote -v

    Conflicts: edit markers → git add → merge --continue / rebase --continue (or --abort).

    Advanced track

    Use this after the basics feel comfortable. These tools save hours on real projects—and can hurt if used carelessly.

    A1. History surgery & power tools Advanced

    git bisect — find the breaking commit

    git bisect start
git bisect bad                # current commit is bad
git bisect good v1.2.0        # known good tag/sha
# Git checks out midpoints; test each time:
git bisect good               # or: git bisect bad
git bisect reset

    Interactive rebase (cleanup before PR)

    git fetch origin
git rebase -i origin/main
# In the editor: pick / squash / reword / drop
git push --force-with-lease
    Warning

    Only rewrite history on branches you alone use.

    Worktrees, sparse checkout, submodules, LFS

    # Second working directory, same repo
git worktree add ../repo-hotfix hotfix/urgent

# Partial clone of huge monorepo
git clone --filter=blob:none --sparse git@github.com:ORG/mono.git
cd mono
git sparse-checkout set apps/web

# Submodule (pin another repo)
git submodule add git@github.com:ORG/lib.git libs/lib
git submodule update --init --recursive

# Large binaries
git lfs install
git lfs track "*.psd"
git add .gitattributes

    Signed commits

    git config --global commit.gpgsign true
# or SSH signing:
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub

    A2. Actions beyond “hello CI” Advanced

    Matrix builds

    jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci && npm test

    Environments, secrets, OIDC (no long-lived cloud keys)

    Use Environments (staging/production) with required reviewers. Prefer OIDC to cloud providers instead of storing static access keys when possible.

    jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      id-token: write   # OIDC
      contents: read
    steps:
      - uses: actions/checkout@v4
      # cloud login action using OIDC here
      - run: ./deploy.sh

    Caching & artifacts

    - uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('**/package-lock.json') }}
- uses: actions/upload-artifact@v4
  with:
    name: build
    path: dist/

    A3. Hardening: rulesets & scanning Advanced

    • Repository rulesets (newer than classic branch protection): block force-pushes, require linear history, require specific status checks.
    • Required reviews + dismiss stale approvals on new commits.
    • Secret scanning / push protection — blocks committing known secret patterns.
    • Code scanning (CodeQL) — finds common vulnerabilities in PRs.
    • Dependabot version updates + security updates.
    # .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }
    Tip

    Start with: 2FA + ruleset on main + required CI check + Dependabot. Add CodeQL when the repo has application code.

    A4. Team workflows that scale Advanced

    • Draft PRs — share work early without requesting formal review.
    • Stacked PRs — small sequential PRs (feature/1 → feature/2) for faster review.
    • Conventional Commits — feat:, fix:, docs: for clearer history and release notes.
    • CODEOWNERS + branch rules — docs owned by docs folks, infra by platform.
    • Releases — tag v1.4.0, generate notes from merged PRs.
    git tag -a v1.4.0 -m "v1.4.0"
git push origin v1.4.0
gh release create v1.4.0 --generate-notes

    A5. GitHub CLI (gh) power moves Advanced

    gh auth login
gh repo view --web
gh pr status
gh pr checkout 42
gh pr diff
gh issue list --label bug
gh api repos/{owner}/{repo}/commits --jq '.[].commit.message'
gh alias set prc 'pr create --fill'

    gh api is ideal for small automations without writing a full scripted client.

    A6. Pages, docs sites & custom domains Advanced

    • Project site — username.github.io/repo/ (this guide).
    • User site — repo named username.github.io serves the root domain path.
    • Custom domain — Settings → Pages → Custom domain; add DNS CNAME/A records; enable HTTPS.
    • Actions-based Pages — build with a static site generator, upload artifact, deploy with actions/deploy-pages.
    # CNAME file at repo root for custom domain
docs.example.com
