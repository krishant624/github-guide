    GitHub Guide: From Zero to Confident

    A practical guide for people who know basic command-line usage but are new to GitHub. Learn why each piece exists, then do it with real commands.

    Self-contained · Works offline · Published with GitHub Pages

    1. Core concepts

    Git vs GitHub

    Git is the version-control tool on your computer. It tracks changes to files as a history of commits.

    GitHub is a hosting service for Git repositories. It adds collaboration: pull requests, issues, Actions, Pages, access control.

    Note

    You can use Git without GitHub (local-only). You cannot meaningfully use GitHub without Git.

    Repository

    A repository (repo) is a project folder tracked by Git. It contains your files plus a hidden .git directory with history.

    Commit

    A commit is a snapshot of your staged changes, with a message explaining why you made them. Commits form a timeline you can inspect and undo.

    Branch

    A branch is a movable pointer to a commit. main (or master) is usually the stable line. Feature branches let you work without breaking main.

    Remote

    A remote is a named URL for a copy of the repo elsewhere. By convention, GitHub’s copy is called origin.

    Fork

    A fork is your personal copy of someone else’s GitHub repo. You push to your fork, then open a pull request back to the original (upstream).

    2. Setup

    Create a GitHub account

    1. Go to github.com/signup.
    2. Verify email and enable two-factor authentication (Settings → Password and authentication).

    Install Git and set identity

    git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase false
git config --list --show-origin
    Tip

    Use the same email as your GitHub account (or a GitHub noreply address from Settings → Emails) so commits link to your profile.

    Authenticate: SSH keys (recommended)

    # Generate a key (press Enter to accept defaults)
ssh-keygen -t ed25519 -C "you@example.com"

# Start agent and add key (macOS/Linux; Windows Git Bash similar)
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# Copy public key, then paste at GitHub → Settings → SSH and GPG keys
cat ~/.ssh/id_ed25519.pub

# Test
ssh -T git@github.com

    Expected test reply includes something like: Hi username! You’ve successfully authenticated…

    Authenticate: Personal Access Token (HTTPS)

    If you use HTTPS remotes, GitHub rejects account passwords. Create a fine-grained PAT: Settings → Developer settings → Personal access tokens.

    Typical scopes for daily work: Contents (read/write), Metadata, Pull requests, Workflows (if you edit Actions).

    Warning

    Never commit a token. Treat it like a password. Revoke it if it leaks.

    3. Creating and cloning repos

    Create on GitHub, then clone

    1. GitHub → New repository.
    2. Choose public/private, add a README if you want a non-empty start.
    3. Clone locally:
    git clone git@github.com:USERNAME/REPO.git
cd REPO

    Create locally, then push

    mkdir my-project
cd my-project
git init
echo "# My Project" > README.md
git add README.md
git commit -m "Initial commit: add README"
git branch -M main
git remote add origin git@github.com:USERNAME/REPO.git
git push -u origin main

    README, .gitignore, LICENSE

    • README.md — what the project is, how to run it, links.
    • .gitignore — files Git should not track (node_modules/, .env, build output).
    • LICENSE — how others may use the code (MIT, Apache-2.0, etc.).
    # Example .gitignore snippets
.env
.env.*
node_modules/
dist/
__pycache__/
*.log
.DS_Store
    Tip

    GitHub’s “Add .gitignore” template when creating a repo is a good starting point for your language.

    4. Daily workflow

    Most days look like this: update → edit → stage → commit → push.

    git status                 # what changed?
git pull                   # get latest from remote (if collaborating)
# ... edit files ...
git diff                   # unstaged changes
git add path/to/file       # stage specific files
# or: git add -p           # stage hunks interactively
git commit -m "Fix login timeout on slow networks"
git push
git log --oneline --graph -n 15

    status / add / commit

    • git status — staged vs unstaged vs untracked.
    • git add — choose what goes into the next commit.
    • git commit — record the snapshot with a clear message (focus on why).

    push / pull / fetch

    • git push — upload your commits to the remote branch.
    • git fetch — download remote updates without merging.
    • git pull — fetch + integrate into your current branch (merge by default with the config above).

    log / diff

    git log --oneline --decorate --graph --all
git diff                   # working tree vs staging
git diff --staged          # staging vs last commit
git diff main...feature    # changes on feature since it diverged from main

    5. Branching and merging

    Feature branch workflow

    git checkout main
git pull
git checkout -b feature/add-search
# work, commit...
git push -u origin feature/add-search

    Merge vs rebase

    • Merge — joins histories; preserves exact branch topology; safe and common on shared branches.
    • Rebase — replays your commits on top of another branch; creates a linear history; avoid rebasing commits already pushed and used by others.
    # Update feature with latest main via merge
git checkout feature/add-search
git fetch origin
git merge origin/main

# Or via rebase (local / your own branch)
git fetch origin
git rebase origin/main
git push --force-with-lease   # only if you already pushed and rewrote history
    Warning

    Prefer --force-with-lease over --force. Never force-push to main on a shared team repo.

    Resolving conflicts

    1. Git marks conflicted files.
    2. Open each file; find <<<<<<< conflict markers; keep the correct code.
    3. Stage and continue:
    git status
# edit conflicted files
git add path/to/resolved-file
git merge --continue          # after a merge
# or: git rebase --continue   # after a rebase
# abort if needed:
# git merge --abort
# git rebase --abort

    6. Pull requests

    A pull request (PR) proposes merging one branch into another and is the review surface for teams.

    Open a PR

    1. Push your branch.
    2. On GitHub: Compare & pull request.
    3. Write a clear title and summary: what changed, why, how to test.
    4. Request reviewers; link issues with Fixes #12.
    # With GitHub CLI (optional)
gh pr create --title "Add search to sidebar" --body "$(cat <<'EOF'
## Summary
- Adds client-side search for guide sections

## Test plan
- [ ] Search filters sections
- [ ] Mobile menu still works
EOF
)"

    Reviewing and requesting changes

    • Comment on lines; ask questions; suggest patches.
    • Approve, comment, or request changes.
    • Author pushes new commits to the same branch; the PR updates automatically.

    Merge strategies

    StrategyWhat it doesWhen to use
    Create a merge commitKeeps all commits + a merge commitWant full history of the branch
    Squash and mergeCombines PR into one commit on mainClean main history; noisy feature commits
    Rebase and mergeReplays commits onto main, no merge commitLinear history; commits already tidy

    7. Collaboration

    Forks and upstream

    git clone git@github.com:YOU/forked-repo.git
cd forked-repo
git remote add upstream git@github.com:ORIGINAL/OWNER-REPO.git
git fetch upstream
git checkout main
git merge upstream/main
git push origin main

    Issues, labels, milestones, assignees

    • Issues — bugs, tasks, discussions tracked on the repo.
    • Labels — bug, docs, good first issue.
    • Milestones — group issues toward a release date.
    • Assignees — who’s responsible.
    • Mentions — @username notifies someone in issues/PRs.

    Projects boards

    GitHub Projects (board/table/roadmap) organize issues and PRs across statuses like Todo → In progress → Done. Link cards back to issues so status stays connected to real work.

    8. Undoing things safely

    GoalSafer command
    Discard unstaged edits in a filegit restore file
    Unstage a file (keep edits)git restore --staged file
    Rewrite last commit message / add forgotten file (not pushed)git commit --amend
    Make a new commit that undoes an old onegit revert COMMIT
    Move branch pointer (dangerous if shared)git reset
    Shelf work temporarilygit stash -u then git stash pop
    Find “lost” commitsgit reflog
     
    # Safe undo of a bad commit already on main: revert
git revert abc1234

# Fix last commit before pushing
git add forgotten.txt
git commit --amend --no-edit

# Stash and come back later
git stash push -m "wip search"
git stash list
git stash pop

# Recover after a bad reset
git reflog
git checkout -b recovery HEAD@{2}
    Warning

    git reset --hard deletes uncommitted work. Prefer restore, revert, and reflog until you know you want destructive reset.

    9. GitHub Actions basics

    Actions run workflows on GitHub’s runners when events happen (push, PR, schedule).

    Create .github/workflows/ci.yml:

    name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: "20"
      - name: Install and test
        run: |
          npm ci
          npm test
    Note

    For a pure HTML guide repo, CI might simply check that index.html exists. Add real tests when you have an app.

    10. Repo settings and security

    • 2FA — turn on for your account; required by many orgs.
    • Branch protection (Settings → Branches) — require PR reviews, status checks, prevent force-push to main.
    • CODEOWNERS — auto-request reviewers for paths.
    • Secrets — Settings → Secrets and variables → Actions. Never store secrets in git.
    • Dependabot — automated dependency update PRs / alerts.
    # .github/CODEOWNERS
*       @your-username
/docs/  @docs-team-handle

    11. GitHub Pages

    Why: host a static site (HTML/CSS/JS) directly from a repo—ideal for guides and docs.

    How (root of main)

    1. Put index.html at the repo root (this guide’s layout).
    2. Add an empty .nojekyll file so GitHub doesn’t process files with Jekyll.
    3. Settings → Pages → Build and deployment → Source: Deploy from a branch.
    4. Branch: main, folder: / (root) → Save.

    Site URL pattern:

    https://USERNAME.github.io/REPO_NAME/
    Tip

    On free accounts, Pages sites from user/org repos are public even if you later change some settings—don’t publish secrets in Pages content.

    12. Troubleshooting

    Updates were rejected (push rejected)

    Remote has commits you don’t. Integrate first:

    git pull --rebase origin main
# resolve conflicts if any
git push

    Detached HEAD

    You checked out a commit, not a branch. Keep work by creating a branch:

    git switch -c recover-work
git switch main

    Merge conflicts

    Edit markers, git add, then git merge --continue or git rebase --continue. Abort with --abort if needed.

    Auth failures

    • SSH: ssh -T git@github.com; check key is added to agent and GitHub.
    • HTTPS: use a PAT, not your GitHub password; update stored credentials.
    • Wrong account: check git remote -v and SSH key associated with the right user.
    git remote -v
git config user.email
# Windows credential manager may cache an old PAT — update or remove it
